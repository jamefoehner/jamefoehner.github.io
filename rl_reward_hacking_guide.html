The five things to know cold 1. Fine-tuning on Claude's labels took a small model from macro-F1 0.35 to 0.665 on human-labeled filings. 2. Reinforcement learning from the untrained model collapsed under both rewards I tried: to "answer nothing" under the accuracy reward, and to a single label under the stricter reward. 3. The same stricter reward did not collapse when started from the fine-tuned model. 4. RL on top of fine-tuning gave 0.64 to 0.73 macro-F1, none of it statistically distinguishable from fine-tuning alone. 5. Every result is a single run on an 89-filing test set, so these are demonstrations of failure modes, not measured rates.

1. The idea

The activist project already had a labeling guide and 100 hand-labeled 13D filings. This study asks a different question: can a small open model learn that labeling task, and what happens when you train it with reinforcement learning (RL) instead of examples?

The interesting part is not the accuracy number. RL optimizes a reward, and a model will find whatever behavior scores well on that reward, including behavior you never intended. That is called reward hacking. This task is a clean place to show it, because the labels are imbalanced and a lazy answer ("none of these") already looks good on a naive accuracy score.

The project was designed in phases: build the data, measure an untrained baseline, fine-tune with examples (SFT), add RL, deliberately try a hackable reward against a better one, and write it up.

2. The task and the labels

Item 4 of a Schedule 13D is where an activist explains what it wants. The model reads that text and outputs a JSON object with ten yes/no fields:

  • board_seats, sale_or_review, breakup_spin, capital_return, operations_costs, management_change, governance, oppose_deal, capital_discipline, engagement_only.

The central rule from LABELING_GUIDE.md: label intent, not boilerplate. Almost every 13D contains a paragraph reserving the right to do anything later; that is not a demand. engagement_only means talks with management and nothing specific, and is never combined with another field.

Three kinds of labels appear in this project, and mixing them up is the easiest way to get confused:

NameWho made themUsed for
Silver labelsClaude Sonnet, using the labeling guideTraining and the RL reward
Gold labelsMe, by handFinal testing only (89 filings)
Dev labelsSilverWatching training progress (37 filings)

Silver agreed with my gold labels about 83% of the time on the LLM evaluation project. That matters: a model trained only on silver labels can at best approach the silver labeler, not exceed it.

The label mix is skewed. engagement_only is on 45% of the gold set and 63% of the training set. Three fields have 5 or fewer gold positives (capital_return, management_change, oppose_deal), so their scores swing a lot.

3. Step 1: Building the data

build_training_data.py pulls filings from the existing campaign data, extracts the Item 4 text, has Sonnet label them, and writes the splits into data/rl/:

I added two options to the build script: --exclude-jsonl (drop filings already in train or dev) and --only-out (write only the extra prompt file without touching the other splits). The gold set is kept completely separate so no model ever sees it during training.

Data caveats to know: about 92% of the pool is amendments (13D/A), with only 159 original filings. ValueAct has a single filing. Also, exclusions.csv has 3 rows, while the plan assumed about 30, and data/proposed_exclusions.csv may hold the rest. I didn't resolve that, so before relying on the "89 of 100" figure, check how the gold set was filtered.

5. Step 3: Supervised fine-tuning (SFT)

SFT means showing the model examples of the right answer and training it to imitate them. sft_train.py does this with LoRA, which trains small add-on matrices instead of all 1.5 billion weights.

  • LoRA settings: rank 16, alpha 32, on all attention and MLP layers; about 18.5 million trainable parameters (1.2% of the model).
  • Training: 3 epochs, learning rate 2e-4, gradient accumulation of 8, 128 optimizer steps. The target for each filing is the silver-label JSON.
  • Result on gold: macro-F1 0.665, exact match 65.2%, mean accuracy 93.5%.

SFT precision is high (0.80 to 1.00 on most fields) but recall is weak on rare fields: capital_discipline 0.22, governance 0.40, capital_return 0.40, oppose_deal 0.40, sale_or_review 0.47. The model plays it safe and leaves labels off. That's the gap RL could try to close.

I trained SFT twice, because the first adapter was lost when the Colab runtime reset. The retrained version reproduced the original almost exactly (0.665 vs. 0.664 macro-F1, identical 65.2% exact match), so all comparisons hold.

6. Step 4: Reinforcement learning (GRPO)

RL doesn't show the model the right answer. It lets the model try answers, scores them with a reward function, and nudges the model toward higher-scoring ones. I wrote a small custom version of GRPO (group relative policy optimization) in grpo_train.py:

  1. Pick a batch of filings.
  2. For each filing, sample 8 different answers from the model (a "group").
  3. Score each answer with the reward function.
  4. Compute each answer's advantage: how much better or worse it scored than the group average, divided by the group's spread.
  5. Update the model to make high-advantage answers more likely and low-advantage ones less likely.

If all 8 answers for a filing score the same, there is nothing to learn from (zero advantage), so those groups are skipped. The log reports this as signal_groups, and it turns out to be a key diagnostic: when it hits 0 for most batches, the model has stopped exploring.

This loop deliberately omits two safeguards common in production RL: a KL penalty (which keeps the model close to its starting point) and clipping (which caps how far a single update can move it). That keeps the code short, but it also makes collapse easier, and it's a limitation I state in the write-up.

The two rewards

RewardHow it scores an answerWeakness
NaiveFraction of the ten fields answered correctly"All no" already scores about 0.84
BetterJaccard overlap of predicted and true positive sets, minus 0.2 if engagement_only is combined with another label; unparseable answers get 0A single-label answer scores 1.0 on many filings

Jaccard overlap is the size of the intersection of two sets divided by the size of their union. Predicting {board_seats} when the truth is {board_seats, governance} gives 1/2.

RL on top of SFT

The first RL runs started from the SFT adapter with gentle settings (learning rate 2e-5, temperature 1.0, small batches). Results on gold:

The 60-step model improves macro-F1 by +0.065 (95% CI [−0.02, +0.17], P(better) = 0.94), so it is suggestive, not significant. Most of the gain is one field: capital_discipline went from F1 0.33 to 0.78. Note that the 30-step model scored lower than SFT, which is a reminder of how noisy a small gold set is.

7. Step 5: The reward-hacking experiments

To test hacking directly, I trained from the untrained base model (no SFT) under each reward, with identical settings: 100 steps, learning rate 5e-5, 4 filings per step, 8 answers each, temperature 1.2, using the training prompts. Only the reward differed.

Naive reward: the model learned to say nothing

The share of dev answers that were all-zero rose from 0% (step 0 and 20) to 19% (step 40), then 70%, 73% and 59% at steps 60, 80 and 100. The naive reward on dev barely moved, staying between 0.87 and 0.93, while the stricter reward fell from 0.73 to about 0.23 to 0.28. On gold:

  • All-zero answers on 66 of 89 filings (SFT: 0 of 89).
  • Macro-F1 0.278 and exact match 16.9%, but mean accuracy still 87.2%.
  • F1 on engagement_only is 0.00 even though it's the most common label.

Against SFT, the paired bootstrap says it is significantly worse on every metric: macro-F1 −0.39 (95% CI [−0.49, −0.24]), exact match −0.48, accuracy −0.06. A dashboard watching only accuracy would have shown a healthy model.

Better reward: it also collapsed, differently

I expected the stricter reward to avoid this. It didn't. Dev macro-F1 fell from 0.32 to 0.14. By step 40 the model answered exactly one label per filing (positives per filing locked at 1.00), and most batches had 0 of 4 groups with any learning signal. On gold:

  • board_seats alone on 55 filings, engagement_only alone on 33, oppose_deal on 1.
  • Macro-F1 0.156, exact match 41.6%, which is below the 44.9% of always guessing engagement_only.
  • Against SFT: macro-F1 −0.51 (95% CI [−0.60, −0.37]), exact match −0.24, accuracy −0.09, all significant.

The dev log was misleading here too: dev exact match climbed to 70% at step 40, which looked like progress. It was just the majority-class rate on a 37-filing dev set.

I originally planned this experiment as "naive reward hacks, better reward doesn't." The data said otherwise, so the write-up says otherwise. That's a more honest and more interesting result.

8. Step 6: The control run

To separate "bad reward" from "bad starting point," I re-ran the better reward with the same aggressive settings (lr 5e-5, temperature 1.2), but starting from the SFT adapter.

Gold setMacro-F1Exact matchMean accuracy
SFT0.66565.2%0.935
Control: SFT + better reward0.64067.4%0.939
Difference (95% CI)−0.026 [−0.13, +0.10]+0.022 [−0.03, +0.09]+0.004 [−0.01, +0.02]
  • No collapse. Positives per filing stayed between 1.05 and 1.30 on dev, and gold answers were varied (46 engagement_only, 12 board_seats, 7 operations_costs, and others).
  • No improvement either. Every difference from SFT is within noise.
  • One field broke. capital_discipline fell to F1 0.00 in this run, versus 0.78 in the gentle run. A plausible reading is that aggressive settings pushed the model to drop its rarest label; with 9 positives and one seed, treat that as a hypothesis, not a finding.

The control comparison between aggressive and gentle RL on top of SFT: the gentle run is better on macro-F1 by +0.091 (95% CI [+0.015, +0.175]). The two runs also differ in batch size and step count, so I can't attribute that gap to one setting.

9. How the results were tested

With 89 test filings, a difference of a few points can be luck. bootstrap_compare.py does a paired bootstrap: it resamples the 89 filings with replacement 2,000 times, scores both models on the same resampled set each time, and records the difference. The middle 95% of those differences is the confidence interval. "Paired" matters, because both models are scored on the same filings, which removes the noise from some filings simply being harder.

The rule I applied: if the interval includes zero, the models are not distinguishable. That is why SFT vs. the control (−0.026, [−0.13, +0.10]) is "no difference" and SFT vs. the 60-step run (+0.065, [−0.02, +0.17]) is "suggestive, not significant."

Metrics: macro-F1 averages the F1 of the ten fields equally, so a rare field counts as much as a common one (good for catching a model that ignores rare labels). Exact match requires all ten fields right at once. Mean accuracy averages per-field accuracy, which is the metric the naive reward effectively optimized, and the easiest to game.

10. What we learned

  1. Cheap supervised training did most of the work. Fine-tuning nearly doubled macro-F1. RL added at most a modest, non-significant gain.
  2. A lazy answer can look excellent. "All no" scores 84% accuracy and 87% for the collapsed model. Always compare against constant baselines.
  3. A better-designed reward can still be hacked. Set overlap made all-zero costly but made a one-label answer cheap.
  4. Starting point decided collapse. The same reward and settings collapsed from the base model and did not from SFT.
  5. The signal vanishes when answers stop varying. Once all 8 samples agree, there is no gradient. A signal_groups count near 0 is the early warning.
  6. Watch several metrics. Accuracy hid the first collapse; exact match and dev reward hid the second.
  7. Be honest when the experiment contradicts the plan. The plan expected the better reward to avoid hacking; it didn't.

11. Mistakes and surprises along the way

  • The gold CSVs were missing from the project folder, so the first build failed. I copied them from an older download and restored exclusions.csv from git.
  • The baseline stalled on the laptop. Automatic device placement was offloading to CPU and disk. I made placement explicit, and the work moved to a Colab GPU.
  • Colab environment issues: a torchao version conflict broke the peft import (fixed with pip uninstall -y torchao); long prompts caused out-of-memory errors during sampling (fixed by sampling in chunks and the --gen_tokens cap); terminal runs don't count as activity, so the idle timeout disconnected me (fixed by running from a notebook cell and saving to Drive).
  • I lost the SFT adapter. It was saved to Colab's temporary storage, which is wiped when the runtime resets. Retraining reproduced it, but lesson: always save outputs to Drive.
  • Commands run in the wrong place. A few Mac-only commands were run in Colab and the reverse; Python pasted into a bash terminal gave syntax errors. Notebook code goes in notebook cells.
  • The plan's assumption about exclusions was off: 3 rows rather than about 30 (see Step 1).

12. Limitations to state up front

  • One run per condition. I have no estimate of run-to-run variation. Dev metrics wobble a lot, for example a dip to 0.29 at one checkpoint that fully recovered.
  • 89 gold filings, with 3 to 9 positives on several fields. One filing can swing a per-field F1 by 0.2.
  • The silver labels cap the ceiling. RL is rewarded for agreeing with Sonnet, not with me.
  • Runs differ in more than one setting, so I can't isolate the cause of the capital_discipline gap.
  • No KL penalty or clipping. Results describe unconstrained RL; a standard setup would probably have limited both collapses.
  • I didn't test why the better reward collapsed. The aggressive learning rate and temperature are my best guess.

13. Next steps

  • Repeat with several seeds for the key conditions, so confidence intervals reflect run-to-run variation.
  • Add a KL penalty and test whether it prevents both collapses from the base model.
  • Redesign the reward: score each field with class weights, or use a macro-averaged reward, so that predicting nothing or one label can't score well.
  • Tune learning rate and temperature separately, to learn which one caused the collapse.
  • Grow the gold set and have a second person label part of it, so rare-field scores are less noisy.

14. How to explain it

30-second version:

I trained a 1.5-billion-parameter open model to label what activist investors demand in SEC filings, using Claude's labels to train it and my own hand labels to test it. Fine-tuning took it from 0.35 to 0.67 macro-F1. Then I tried reinforcement learning from the untrained model and watched it cheat: with an accuracy reward it learned to answer "no demands" on most filings and still scored 87% accuracy, and with a stricter reward it collapsed to a single label. Starting from the fine-tuned model avoided the collapse, but didn't significantly improve on it.

One-minute version:

The task is tagging 13D filings with ten demand categories. Most labels are zero for most filings, so a model that always says "none" already gets 84% accuracy. I built the data with Claude as a labeler and kept 89 hand-labeled filings strictly for testing. LoRA fine-tuning lifted macro-F1 from 0.35 to 0.665. For reinforcement learning I wrote a small GRPO loop and compared two rewards, starting from the untrained model. The accuracy reward drifted to all-zero answers on 66 of 89 test filings, while accuracy stayed at 87%. My stricter set-overlap reward collapsed to one label per filing and scored below always guessing the most common label. A control run starting from the fine-tuned model didn't collapse, and a gentler RL run reached 0.73 macro-F1, but a paired bootstrap says that's not distinguishable from fine-tuning alone. These are single runs on a small test set, so I present them as failure modes, not rates.

15. Interview questions to prepare for

Isn't it circular to train on Claude's labels?
It would be if I tested on them. I test only on 89 labels I made by hand and the model never saw. The caveat is that the model can at best approach Claude's labels, which agreed with mine about 83% of the time.
Why did the "better" reward collapse?
I haven't isolated it. A one-label answer scores a full 1.0 on a large share of filings, since engagement_only is the majority class, and my aggressive learning rate and temperature with no KL penalty likely pushed the model there. Once all 8 sampled answers agree, there's no learning signal. I'd test a KL penalty and a class-weighted reward next.
Why did starting from SFT avoid collapse?
The SFT model already produced varied, mostly correct answers, so it had a good policy to stay near. The base model had no such anchor. I can say that from the control run; I haven't tested the mechanism further.
Did RL actually help?
Not provably. The best run improved macro-F1 by 0.065, but the 95% interval includes zero, exact match was identical, and most of the gain was one rare field with 9 test examples.
How do you know the results aren't just noise?
I used a paired bootstrap on the same 89 filings. The collapses are far outside noise (intervals exclude zero). The small gains aren't, and I say so. The weakness is one seed per condition.
Why track more than accuracy?
Because accuracy rewards the majority answer. The collapsed model had 87% accuracy and half the F1 of a model that actually labels. I added constant baselines and macro-F1 specifically to catch that.
What would you do with more time?
Run multiple seeds, add a KL penalty, redesign the reward so empty and single-label answers can't score well, and expand the gold set with a second labeler.

16. Key terms

Reward hacking
A model finding a behavior that scores well on the reward without doing the intended task.
Mode collapse
A model's answers converging to one or two outputs regardless of input.
SFT (supervised fine-tuning)
Training a model to imitate example answers.
LoRA
Fine-tuning by training small added matrices instead of all weights; cheap and easy to save as an "adapter."
GRPO
An RL method that samples a group of answers per prompt and compares each to the group average, with no separate value model.
Advantage
How much better an answer scored than its group's average, scaled by the group's spread.
KL penalty
A term that penalizes the model for drifting from a reference model; a standard guard against collapse.
Silver vs. gold labels
Labels from an automatic labeler (Claude) versus labels made by hand and used only for testing.
Precision, recall, F1
Of the labels predicted, how many were right; of the true labels, how many were found; and their harmonic mean.
Macro-F1
The average F1 across the ten fields, weighting rare and common fields equally.
Exact match
The share of filings where all ten fields are right at once.
Jaccard overlap
Size of the intersection of two sets divided by the size of their union.
Paired bootstrap
Resampling the test filings many times and comparing two models on the same resamples to get a confidence interval.
Parse rate
The share of model outputs that were valid JSON with all ten fields.
